# Crosscheck

把 Agent 作为编排者，把仓库中的确定性 CLI 作为执行工具。不要让模型替代测试引擎做断言、数据库清理或结果判定。

默认唯一业务执行入口是 `run_suite.py`。Excel/CSV/JSON/case-gen YAML 只能先导入 canonical suite；旧 `run_batch.py --excel` 仅用于兼容和迁移诊断，不得用于新套件正式验收。

## 执行模式

默认使用 **pipeline mode**，而不是逐步确认模式。Agent 应：

- 开始时用一句话说明流水线阶段和当前假设；
- 自动读取已有 profile、用例、readiness、登录态和配置的**存在性**，不输出秘密；
- 对安全的只读步骤连续执行，不在每个步骤结束后等待用户；
- pilot 达到安全扩批条件后，立即批量执行所有当前 READY 用例，不询问“是否继续”；
- 遇到多个可选项时选择最小风险、最小范围、可回滚的默认值；
- 只有真正阻塞后续执行的问题才提问，并尽量一次问完一组问题；
- 每隔一个阶段或发生阻塞时汇报进度，不把正常阶段变成确认对话。

默认阶段链：

```text
发现上下文
  → 本地安装预检
  → workspace/profile/用例检查
  → 套件指纹、意图分类与 UI/API/DB 覆盖规划
  → 环境 preflight
  → 登录态检查/必要时重登
  → dry-run 或建模
  → 最小范围执行
  → 报告与清理检查
  → 根据结果自动扩大、重试或停止
```

详细状态机见 `references/pipeline.md`。

## 强制流程

严格按以下阶段执行，不得跳过信息收集直接跑测试。

如果用户提供的是 Excel/CSV/JSON 散文用例，执行 `scripts/import_suite.py`；如果是 case-gen YAML，执行 `scripts/import_casegen.py`。转成隔离 canonical suite 后评分、补齐绑定、计算 approval content_hash，再由 `run_suite.py` 编译和执行。不要继续把共享 `workspace/specs_verified` 当作新套件规格目录。

### 1. 收集信息（自动优先）

先提取用户已经提供的信息，再读取本地已有信息。不要为了填满清单而提问；能从 profile、workspace、命令帮助、文件名或前序结果确定的内容直接使用。

必须收集：

1. **测试目标**：要验证的系统、业务模块、功能或问题。
2. **环境边界**：确认是开发、测试、预发布等非生产环境；记录站点 URL。
3. **认证方式**：人工登录、账密登录、SSO、验证码、2FA，是否允许保存测试登录态。
4. **用例来源**：Excel、CSV、JSON、已有规格，或需要从自然语言整理。
5. **数据库条件**：数据库类型、只读连接是否可用；是否需要写入测试以及是否有独立低权限写账号。
6. **代码与接口资料**：是否有后端源码、OpenAPI、接口文档或可供抓包的页面。
7. **执行范围**：只做环境扫描、查询对账、UI 验证、写入流程，还是完整回归。
8. **工作目录**：使用已有 workspace 还是创建新的 workspace；给出绝对路径或可解析路径。
9. **安全确认**：workspace 是否来自可信来源；是否需要执行其中的 Python 脚本。
10. **交付期望**：只要报告，还是还要缺陷清单、环境缺口、可复跑规格和发布包。

使用 `references/intake.md` 中的分层问法。不要索要用户直接在聊天中粘贴密码、Cookie、Token 或数据库口令；让用户把秘密写入本地 workspace 配置。正常情况下只在阻塞时提问。

### 2. 复述并确认（仅阻塞时）

把收集结果整理成“接入摘要”，至少包含：

- 目标与范围；
- 环境及明确的非生产确认；
- 可用输入；
- 登录与数据库能力；
- 计划执行的命令阶段；
- 风险项和仍缺失的信息。

以下是**硬门禁**，不是每阶段确认点。已由用户前文明确确认、profile 明确标识或本地 preflight 可靠证明的内容，不要重复询问：

- 用户明确确认不是生产环境，或用户已经在当前任务中明确授权该测试环境；仅凭域名猜测不能替代确认；
- workspace 路径明确；
- 若涉及数据库写入，存在独立低权限测试账号；
- 若涉及 workspace Python 脚本，用户明确确认来源可信；
- 不需要在对话中暴露秘密。

只有硬门禁无法从上下文或本地资料确认时，才暂停并提问。提问应一次覆盖所有当前阻塞项；用户回答后继续流水线，不重新从第一阶段开始。

### 3. 检查本地安装（自动执行）

在项目根目录执行：

```powershell
python scripts/preflight_install.py
```

失败时按输出修复。首次安装参阅 `references/commands.md`。不要在安装预检阶段访问业务系统。

### 4. 准备 workspace（自动执行非破坏性操作）

已有 workspace 时自动检查结构和缺口，避免覆盖用户文件。明确要求新建且目标不存在时执行：

```powershell
python scripts/init_workspace.py <workspace>
```

秘密只能写入：

- `<workspace>/config/credentials.yaml`
- `<workspace>/config/db.yaml`
- `<workspace>/.auth/`

不得把秘密复制到报告、回复、Skill 或仓库文件中。详细结构见 `references/workspace.md`。

### 5. 选择最小执行路径（自动选择）

不要默认执行完整回归。根据用户目标和已有资料自动选择最小路径；如果用户没有指定范围，默认先执行 preflight、登录态检查、dry-run，再执行最多 3 条非破坏性或已配置清理的用例。不要因为没有逐步确认就扩大到完整回归。

- **仅收集缺口**：`run_onboard.py scan`
- **环境体检**：`run_preflight.py`
- **建立登录态**：`run_verify.py login`
- **页面抓包与查询建模**：`run_verify.py probe`
- **查询接口与数据库对账**：`run_verify.py reconcile`
- **用例草拟/检查**：`run_batch.py --dry-run`
- **只做分类与层覆盖规划**：`run_batch.py --plan-only`
- **指定用例执行**：`run_batch.py --only ...`
- **完整编排**：`run_crosscheck.py`

具体参数和选路规则见 `references/commands.md`。

执行 Excel 前必须先生成 `suite_plan.json`/`suite_plan.md`。如果用例要求 UI、API 或 DB 而规格未提供对应层，必须在报告中标记覆盖缺口；不得把 API-only 结果描述为三层验证。套件指纹变化时，将其视为新套件，旧 case_id 路由和旧人审规格必须经过标题语义校验。

### 5.1 自动扩批（默认行为）

pilot 完成后不要停下来等待用户。满足以下条件时自动进入批量执行：

- 至少 1 条 pilot 完成预期层验证并 PASS；
- 登录态、API、数据库连接正常；
- 没有清理失败、未声明表变更或安全门禁失败；
- 后续规格为 `human_verified` 且非 `blocked`；
- 写入用例具备 `cleanup` 和 `allowed_tables`；
- UI 用例使用当前套件标题一致的规格。

扩批范围是**所有当前 READY 用例**，不是强行执行所有 Excel 行：

- 先批量执行查询/reconcile；
- 再串行执行 UI、流程和写入用例；
- `draft`、`blocked`、覆盖层缺失的用例进入缺口报告，不逐条询问；
- 单条业务 FAIL 记录证据后继续执行其他相互独立用例；
- 清理失败、登录整体失效、环境污染或连续 3 条同类环境错误时熔断。

只有用户明确要求“仅试跑”“只跑指定用例”或设置 `--limit/--only`，才在限定范围后停止。用户说“测试这批用例”“继续测试”或未限制范围，均视为授权自动扩批 READY 集合。

### 6. 写操作安全门禁（唯一需要人工确认的常见阶段）

任何写入/UI 提交流程开始前，逐项确认：

- 使用隔离测试环境；
- 写连接是独立最小权限账号；
- 规格已 `human_verified`；
- `cleanup` 非空且只包含预期清理目标；
- `allowed_tables` 非空；
- 默认启用清理；
- 用户没有要求绕过安全限制。

默认禁止 `--no-cleanup`。只有用户明确要求保留现场、理解残留数据风险且说明清理方式时才可使用。若用户已经在当前任务中明确要求保留现场，则不重复询问，但仍在报告中标红。

默认禁止 `--allow-workspace-scripts`。只有用户明确确认 workspace 可信且任务确实需要脚本时才可使用。它不是沙箱。没有脚本需求时不要询问这个问题。

### 7. 执行与观察（自动推进）

先窄后宽，阶段之间自动推进：

1. 预检或 dry-run；
2. 单个/少量用例；
3. 检查报告和清理状态；
4. pilot 通过后自动扩大到当前 READY 用例集，不再请求确认；只有用户明确限定为试跑时才停止。

失败时先自动分类：可重试的环境问题重试一次；缺配置、需要人工登录、写权限不足或安全门禁失败则停止并一次性报告阻塞原因；业务 FAIL 不自动重复执行写入用例，但不阻止其他独立 READY 用例继续执行。

不得把 `SKIP`、`ENV_ERROR` 或 `ABORTED` 表述为通过。不得仅依据页面提示判定数据库一致性。

### 8. 汇总结果

读取运行目录中的结构化结果和报告，区分：

- PASS；
- FAIL；
- 环境问题；
- 未建模/未人审；
- 清理失败或残留；
- 疑似真实缺陷。

最终回复至少给出：运行范围、通过/失败/跳过统计、关键证据路径、风险与下一步。报告解释规范见 `references/reporting.md`。

## 禁止事项

- 不在未确认环境时访问目标系统。
- 不连接生产数据库或使用生产账号。
- 不要求用户在聊天中发送秘密。
- 不输出配置文件中的密码、DSN、Cookie、Token 或完整请求头。
- 不执行来源不明的 workspace Python 文件。
- 不手工压缩整个项目目录交付；发布必须使用 `python scripts/build_release.py`。
- 不自动修改真实业务配置后直接执行写入测试，必须先让用户确认摘要。
- 不因“pipeline mode”绕过非生产、写入、清理和脚本信任硬门禁。

# 信息收集

## 原则

- 先使用对话和本地文件中已有的信息，只问真正缺失的内容。
- 默认不发问。先读取上下文和本地配置；只有硬门禁缺失时才一次性问完当前阻塞项。
- 若必须发问，第一轮控制在 5 至 8 个问题；通常应少于 3 个。
- 不索要秘密值。只问秘密应保存到哪个本地配置，或让用户自行填写模板。
- 用户说“直接跑”时自动执行所有安全的只读阶段；不能跳过非生产环境、写入、清理和脚本信任硬门禁。

## 第一轮信息模板

可以按任务删减后询问：

1. 要测试哪个系统和哪些功能？成功标准是什么？
2. 目标 URL 是什么？请确认它是开发、测试或预发布环境，不是生产环境。
3. 登录是人工、账密、SSO、验证码还是 2FA？是否允许在本机保存测试登录态？
4. 用例在哪里：Excel/CSV/JSON/已有规格，还是需要先整理自然语言需求？
5. 是否需要数据库对账？数据库类型是什么，是否有只读测试账号？
6. 是否包含新增、提交、审批等写操作？如有，是否有独立低权限写账号并允许清理测试数据？
7. 是否有源码、OpenAPI、接口文档或可操作页面？
8. 使用已有 workspace 还是新建？路径是什么？

## 第二轮条件问题

仅在相关时询问：

- 多角色、审批链或 impersonate：需要哪些测试角色？
- 有验证码/2FA：是否由用户在打开的浏览器中人工完成？
- 多数据库：每个功能对应哪个只读库，哪个写库？
- 写操作：允许改动和清理哪些表？是否有异步任务或消息延迟？
- workspace 脚本：来源是谁，是否经过审核，是否明确允许执行？
- 报告：需要 HTML、缺陷清单、环境缺口、截图/录像中的哪些内容？

## 接入摘要模板

```text
目标：<系统/模块/成功标准>
环境：<环境类型和 URL>；非生产确认：<是/否>
认证：<方式和是否允许保存登录态>
用例：<来源和路径>
数据库：<类型、只读/写入能力，不包含秘密>
资料：<源码/OpenAPI/页面>
workspace：<路径，新建或已有>
计划：<预检 → 登录 → 探测 → dry-run → 小批执行 → 完整执行>
脚本权限：<默认禁止/用户已确认可信>
交付物：<报告/缺陷/缺口/规格>
待补充：<缺失项>
```

摘要未经用户确认时，仍可执行已由用户上下文明确授权且属于安全只读范围的阶段；无法确认非生产环境、人工登录或写入权限时必须暂停。不要为了确认摘要而重复询问已经明确的信息。

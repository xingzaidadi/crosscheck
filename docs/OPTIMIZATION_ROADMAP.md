# Crosscheck Alignment Audit and Optimization Roadmap

审计日期：2026-11-12。范围：当前工作树、历史运行证据、Skill 与 case-gen 输出约定。
这是一份设计审计，不代表下列目标能力已经实现；本次未访问业务系统或修改测试数据。

## 1. 总结

问题不在 Excel 本身，也不在模型偏好。真正的问题是多条入口使用不同数据契约，且规划、审批、执行、证据与业务结论没有形成一个受程序约束的闭环。

保留 Excel/CSV/Markdown/自然语言作为用户输入，统一归一化成版本化 YAML 业务用例，再编译成类型化执行计划。禁止 Excel 路径绕过统一校验直接执行。

当前定位：已有 UI/API/DB 执行机制的工程原型，不是任意用例开箱即跑的成熟通用测试产品。此前 8.5/10 的综合评分缺少客观验收依据，不宜作为成熟度结论。81 个脚本测试通过也不等于复杂业务验收通过。

## 2. 格式决策

|层|目标格式|用途|
|---|---|---|
|用户原始输入|Excel/CSV/case-gen YAML/Markdown|保留用户工作习惯，不直接作为执行命令|
|业务意图|版本化 canonical YAML|Given/When/Then、角色、预期、来源、待确认规则|
|系统绑定|独立 YAML 连接器与配方|页面、接口、字段、身份、数据准备和清理|
|执行计划|经 Schema 验证的 JSON|明确动作顺序、变量类型、断言、依赖、权限与执行哈希|
|运行结果|JSON 事件与结果|机器判定、断点续跑、CI 退出码、证据索引|
|用户展示|Markdown/HTML，按需导出 Excel|可读报告，不作为事实源|

一个需求/用例只保留一个 canonical 事实源。源文件只读保留；编译产物可以删除重建；禁止多处手工修改同一业务规则。

## 3. 当前未对齐项

### P0：影响结果真实性或安全

1. **DSL 到执行器未接通。** `core/suite_dsl.py` 提供加载和评分，没有实际 compiler；`run_suite.py` 直接转调 `run_batch.py --specs`。不能称为 canonical 用例可执行。
2. **评分不约束执行。** `run_suite.py` 写评分后，只要 specs 目录存在就执行，没有验证每份 spec 与 canonical case 的状态、suite_id、内容哈希关系。
3. **通用 mapping 被当作专用用例。** `modeler` 可以因映射已人审而将当前用例自动设为 human_verified。已有列表对账无法证明转办、订单占用或组合失败，必须分离连接器复用与用例审批。
4. **空数据可造成空验证通过。** 待下单页面和接口均无数据时，空集合一致只能证明空状态一致，不能证明 TC03 预期的三条行和 count=2。此前这类 PASS 不能作为完整业务验收。
5. **规划层存在不等于实际覆盖。** `suite_plan._provided_layers` 从 mode、url_pattern、db/feature 等推断能力，不能证明抓到了指定请求、执行了 DB 查询或命中了专用断言。
6. **suite 目录隔离尚未贯穿解析。** 底层仍使用 workspace 全局 config、mapping、recipe 和登录态；ID/标题相同不等于来源可信。编译器和执行器必须使用同一个 SuiteContext。
7. **Skill 状态机尚非运行器状态机。** pilot、自动扩批、熔断、恢复和停止条件主要在提示词里；run_batch 的循环和退出码不能充分证明这些策略得到执行。
8. **写入与清理需要更强门禁。** UI 写入分支获取 has_write 但没有像 API 分支一样拒绝无写连接；清理登记册损坏会被当作空登记册；删除 LIKE 模式未转义 marker 中的下划线等通配符；重试清理应重验持久化目标。

### P1：影响通用性和交付

9. **case-gen Schema 不兼容。** 它通常输出 metadata/test_model/cases/coverage_map，当前 importer 仅按 Excel/CSV/JSON RawCase 读取；不支持直接导入该 YAML。
10. **评分/READY 规则不可靠。** 结构评分把非空占位块视为能力；ready 结果不严格依赖 case.status；不同层数可得分上限不同，三层完整内容甚至可能超过 100。必须换成硬校验加分维度展示。
11. **业务字段进入 core。** `_apply_actor_context` 硬编码 applicantUserId/demanderUserId 等字段。身份替换应由连接器字段绑定声明，不应成为通用内核语义。
12. **默认猜测环境。** importer 写 environment=test 并不能证明目标为测试环境。缺失环境应是 unknown；执行授权应绑定真实目标指纹。
13. **case ID 和路径混用。** canonical ID 带 suite/ 前缀，而 engine 将 case_id 拼成目录名。需要稳定 UUID/slug 与 display_key 分离、路径限制和重复 ID 校验。
14. **证据关联不足。** 需要 case→step→request→DB query→assertion→cleanup 的链路、时间戳和环境身份。按 URL 模糊选最后一个 XHR 不足以绑定页签、参数、分页和竞态请求。
15. **审批语义错位。** human_verified 应由明确审批记录产生，不能因为模板装配成功就自动写入。支持按风险配置一次审批策略，避免逐条询问用户。
16. **测试覆盖与结论不对称。** 部分测试重复实现被测逻辑而不调用生产函数。要测试实际 CLI、隔离边界、故障注入和“不应 PASS”的情况。
17. **报告聚合不一致。** 自定义 run_id 与只扫描 run_* 的索引不一致；summary 需要包含 cleanup、覆盖不足、失效执行和业务断言数量，不能仅统计 pass/fail。

### P2：用户体验和扩展

18. Skill 应自动补建模并循环执行，直到全部结案或只剩硬阻塞，不应把 READY 集合暂时为空视为任务完成。
19. 一个统一入口与机器可读诊断；其他脚本保留为内部子命令或兼容包装。
20. 文档中去除固定业务数量、历史终态清单数字、未实现功能表述与迁移期双轨描述。
21. 发布采用明确源码允许清单、内容级秘密扫描和包解压安装验收；测试 fixture 不应获得整个目录的敏感路径豁免。

## 4. 目标职责边界

### 输入适配层

负责 Excel 多 sheet/列映射、case-gen YAML、JSON、CSV 导入，保留 source hash/row/revision。
输入缺少角色、数据和验收信息时保留缺口，不自动编造表名、接口、环境和业务规则。

### Canonical 业务用例层

用户主要维护 Given/When/Then、期望结果与资料引用，不必亲自填写 selector 和 SQL。
不能仅靠改 YAML 格式使隐含规则变明确；未知值用 unresolved 节点和 owner 标识。

### 项目连接器层

隔离页面模型、API 契约、DB schema、角色授权、fixture recipe、事件触发和清理配方。
连接器带 system/version/environment/tenant/schema 指纹和有效期；默认不跨套件隐式继承，复用必须显式声明并重新校验。

### 编译与审批层

将意图映射成可执行步骤；缺失动作、无效 fixture、未解析变量、不支持的 operator、没有专用 oracle 都应报出。
每个验收项有 assertion_id，每个 assertion 有来源和观测层，每个测试前提有准备或只读验证步骤。
审批绑定编译内容哈希，内容变化使审批失效；连接器已审核不代表所有业务用例已审核。

### 执行层

只消费已校验计划，不读取任意历史 workspace 作为兜底。支持依赖图、幂等、超时、轮询、熔断、清理和恢复。
pilot 选择有代表性的风险/路径，不能一个空列表查询通过就批准所有流程写入。
业务失败继续独立用例；共享前提失败只阻断依赖；清理或安全失效停止相关写入范围。

### 结果层

分离 CASE_PASS、CASE_FAIL、PARTIAL、BLOCKED、INVALID_SPEC、ENV_ERROR、NOT_RUN。
用例通过必须所有必需前提和断言真实执行成功；无断言、预期非空而实测空、仅采集未比较均不得 PASS。
报告展示计划覆盖和已验证覆盖；三层不是强制每条都有，按风险选择最小充分证据。

## 5. 复杂用例处理

将多角色/跨系统用例拆成可组合配方，而不是无限增加每条用例的自由代码：

- Fixture：创建指定业务状态，返回带类型的资源句柄和清理句柄。
- Actor：角色到连接器身份/会话的绑定，禁止复制固定历史用户名。
- Action：具名业务动作到 UI/API/event driver。
- Oracle：独立于被测实现的业务判据，如数量等式、状态机、决策表与无副作用校验。
- Dependency：状态前提、共享资源和先后关系；无法准备则注明原因和责任方。

例如 TC34 必须覆盖实际转办、原记录失效、新记录生效和角色权限变化。普通列表一致性不得替代其中任何一项。
TC03 必须验证指定条件的需求行及 count=2；没有 fixture 时只允许作为单独的空状态 smoke，不复用原 TC03 的 PASS。

## 6. 推荐迁移顺序

|阶段|交付|完成标准|
|P0-A 结论纠偏|历史报告追加失效/部分覆盖说明、修复空验证 PASS 和退出码|历史错误样本重跑不能再判 CASE_PASS|
|P0-B 唯一契约|Schema v1、状态/ID/路径/类型校验、评分拆分|未知字段/重复 ID/不支持 operator/不完整 ready 均拒绝|
|P0-C 唯一编译路径|所有输入归一化、compiler、SuiteContext、审批与哈希|同一用例由 Excel 和 YAML 输入生成等价计划；跨套件污染被拒绝|
|P1-A 确定性执行|计划执行器、pilot/批量/补建模循环、依赖与熔断|不用 Agent 人工接力也能执行并恢复；有限重试有真实测试|
|P1-B 场景配方|只读查询→写入→角色→异步→事务组合|TC03/10/11/20/34/54 各有专用前提、动作和判据|
|P1-C 统一结果|JSON 事实源、HTML/MD/Excel 展示、CI 集成|PASS 可追溯到逐条断言；部分覆盖不可冒充完成|
|P2 通用性验收|两个无关业务域完整接入、包安装验收|不改 core，仅替换连接器/配方，跑通同一流水线|

旧脚本不立即删除。改成调用统一 importer/compiler/runner 的兼容包装，提供迁移诊断；禁止新能力继续只接旧 Excel 路径。

## 7. 验收与评分方向

取消凭感觉给“8.5/10”的成熟度分。分开报告：

1. 结构合规率：Schema 校验通过比例。
2. 编译成功率：无未解析绑定、且审核有效的计划比例。
3. 业务充分率：验收项有独立可执行判据的比例。
4. 前提就绪率：fixture 准备与状态验证成功比例。
5. 实际覆盖率：已执行必需断言/总必需断言。
6. 自动推进率：无需人工操作完成的非阻塞步骤比例。
7. 清理成功率：已验证释放资源/创建资源。
8. 通用性：新增业务是否不改 core、连接器成本及隔离负向测试通过率。

交付门槛必须包含负向实验：旧套件同 ID、源码改动、身份变化、空返回、找错接口、无 DB 权限、清理失败、服务重启、断言错误、用例部分成功。
验收目标是“错误绝不被静默当成通过”，而不是让尽可能多的 Excel 行显示绿色。

# AI 可执行用例工程方案与输入诉求

> 目标：让 AI 能稳定理解用例，让 Crosscheck 能确定性执行用例，让业务、测试和开发能够共同审查用例是否完整、真实、可复跑。

## 1. 结论

用例确实是当前工具链的主要瓶颈之一，并且会直接影响：

- 自动建模效率；
- READY 用例比例；
- 执行成功率；
- 失败归因准确率；
- UI/API/DB 证据完整性；
- 武器库依赖规划；
- 回归维护成本。

但更准确地说，瓶颈不是“没有用例”，而是：

> 人类可读的散文用例，没有稳定表达成 AI 可理解、框架可编译、执行器可判定的业务契约。

当前 Crosscheck 已经具备 Excel/CSV/JSON 导入、canonical suite、哈希审批、断言绑定、UI/API/DB 证据和知识依赖，因此基础方向正确；不足之处在于导入过程大多只是把散文搬进 canonical 草稿，无法自动补足业务事实、对象身份、前置数据、状态转换、精确断言和清理方式。

建议把“用例设计”升级为独立产品能力：**Executable Case Engineering（可执行用例工程）**。

## 2. 当前能力审计

### 2.1 当前已经做得好的部分

1. 支持 Excel、CSV、JSON 和 case-gen YAML 输入。
2. 输入会转成隔离的 canonical suite，避免旧用例和旧路由污染。
3. 用例有 `draft/ready/blocked` 状态和 `human_verified` 审批。
4. 用例内容、知识和 connector 变化后，旧审批会失效。
5. UI/API/DB 断言必须绑定实际 proof，不能只写一句预期。
6. 写操作要求清理和 `allowed_tables`。
7. 有 suite readiness、评分、覆盖层和缺口诊断。
8. AI 可以辅助生成草稿，但正式执行由确定性引擎完成。

这些机制说明 Crosscheck 已经不是“读 Excel 直接点页面”，而是具备可执行规格的雏形。

### 2.2 当前不足

#### A. 原始用例信息密度太低

常见用例只有：

```text
用例名称：发布策略
前置条件：存在需求
步骤：进入策略页面，填写数据并提交
预期：发布成功
```

AI 无法可靠知道：

- 哪种需求可以使用；
- 需求要处于什么状态；
- 使用哪个角色；
- 入口页面和操作对象是什么；
- 哪些字段必填，值从哪里来；
- 成功后状态、编号、关联关系是什么；
- 页面、接口、数据库分别验证什么；
- 是否允许复用已有数据；
- 失败后如何清理或补偿。

#### B. 分类仍依赖关键词

当前意图和 UI/API/DB 层分类主要根据“创建、页面、接口、数据库”等词推断。它适合生成初步计划，但不能替代业务契约。例如“点击发布并确认状态”为 UI 操作，却可能没有写“页面”；“验证策略落库”也可能没有明确写“数据库”。

#### C. 预期结果不可判定

“成功”“正常展示”“数据正确”“提示合理”不是机器可判定的断言。框架需要明确：

```text
字段/对象 + 运算符 + 期望值 + 数据来源 + 等待策略
```

#### D. 前置条件没有对象化

“存在已审批需求”目前经常只是一段文本，没有转换为：

```yaml
object: requirement
state: APPROVED
conditions: {...}
strategy: create
```

因此无法稳定接入业务测试武器库。

#### E. 用例粒度不稳定

一条用例可能同时包含创建需求、审批、发布策略、发布招采和校验，导致：

- 失败点不清楚；
- 重试可能重复造数；
- 用例执行时间长；
- 上游失败被误判为目标节点失败；
- 相同前置流程无法复用。

#### F. 缺少需求—规则—用例—证据追踪

目前可以记录 source 文件和行号，但还缺少稳定的：

```text
需求/规则 ID → 测试点 → 用例 → 能力 → 断言 → 运行证据 → 缺陷
```

这会影响覆盖率判断和变更影响分析。

## 3. 我需要什么样的用例

我最需要的不是更多自然语言，而是**最少但完整的业务事实**。理想用例分两层：

### 3.1 业务层：人负责确认“测什么”

业务层必须提供：

| 信息 | 示例 | 为什么需要 |
|---|---|---|
| 业务目标 | 发布采购策略 | 确定被测节点 |
| 来源规则 | PRD-123 / RULE-07 | 可追踪和变更分析 |
| 目标角色 | 策略管理员 | 权限和登录态 |
| 前置对象 | 已审批需求 | 依赖规划 |
| 关键条件 | 金额≥10万、采购部 | 数据选择/创建 |
| 核心动作 | 发布策略 | 被测动作，不能被 DB 绕过 |
| 成功结果 | 策略状态=PUBLISHED | 可判定结果 |
| 失败结果 | 无权限返回 403/按钮不可见 | 负向断言 |
| 副作用 | 生成策略编号并关联需求 | 验证范围 |
| 清理政策 | 可取消，不允许物理删除 | 测试数据生命周期 |

业务人员不需要写 CSS selector、SQL 或 JSONPath，但必须确认业务真相。

### 3.2 执行层：AI 草拟、工具探测、人审核“怎么测”

执行层包括：

- 页面入口和稳定定位器；
- API 方法、URL、请求字段、响应字段；
- DB 表、主键、状态字段和关联关系；
- 前置能力和输出变量；
- 精确断言和等待策略；
- 证据、清理和补偿；
- 幂等键、重试和失败分类。

这部分不要求业务人员手写。AI 可以结合录制、接口文档、源码、数据库 schema 和既有知识生成草稿，但必须经过 deterministic 校验和人工审批。

## 4. 推荐的用例模型

用例应遵循：

```text
Trace → Intent → Preconditions → Action → Oracle → Evidence → Cleanup
```

推荐 canonical 示例：

```yaml
schema_version: 2
case_id: strategy-publish-001
title: 已审批需求发布采购策略
suite_id: sourcing-strategy-v1
priority: P0
status: draft

traceability:
  requirements: [PRD-123]
  rules: [RULE-STRATEGY-07]
  risks: [RISK-DUPLICATE-PUBLISH]

intent:
  target_object: strategy
  target_action: publish
  scenario: happy_path
  under_test: strategy.publish

actors:
  operator:
    role: strategy_manager
    profile: test-system

preconditions:
  - ref: requirement
    object: requirement
    state: APPROVED
    strategy: create
    conditions:
      department: 采购部
      amount: {gte: 100000}
    outputs: [id, code, status]

action:
  capability: strategy.publish
  inputs:
    requirement_id: "{{ requirement.id }}"
    strategy_name: "AUTO-{{ run.id }}"

oracles:
  - id: A-UI-001
    subject: ui.strategy.status
    operator: equals
    expected: 已发布
    proof: ui
  - id: A-API-001
    subject: api.response.data.status
    operator: equals
    expected: PUBLISHED
    proof: api
  - id: A-DB-001
    subject: db.strategy.status
    operator: equals
    expected: PUBLISHED
    proof: db
  - id: A-REL-001
    subject: db.strategy.requirement_id
    operator: equals
    expected: "{{ requirement.id }}"
    proof: db

wait:
  until: A-DB-001
  timeout_s: 30
  interval_s: 2

evidence:
  required: [screenshot, api_request, api_response, db_result, lineage]

cleanup:
  capability: strategy.cancel
  policy: always

approval:
  status: draft
  content_hash: ""
```

## 5. 用例设计原则

### 5.1 一条用例只验证一个主要业务结论

可以包含前置依赖链，但 `under_test` 只能有一个主要目标。比如发布策略用例中，创建和审批需求是前置，不算策略发布失败。

### 5.2 前置条件必须对象化

禁止只写“准备一条数据”。必须声明对象、状态、约束、创建/复用策略和输出。

### 5.3 预期结果必须可判定

禁止：

```text
发布成功
展示正常
数据正确
```

应改为：

```text
策略状态=PUBLISHED
策略编号非空且满足格式
策略记录 requirement_id=上游需求 ID
重复提交只生成一条策略记录
```

### 5.4 区分业务断言和实现证据

“状态=PUBLISHED”是业务断言；“数据库 strategy.status 字段”为其中一种 proof。用例首先描述业务真相，再绑定当前系统中的页面/API/DB 实现。

### 5.5 正向、负向、边界、权限、幂等成组设计

每个关键动作至少评估：

- 正常路径；
- 缺失/非法输入；
- 边界值；
- 角色和数据权限；
- 重复提交和幂等；
- 状态不允许时的拦截；
- 异步超时和失败恢复；
- 审计和副作用。

不要求每个动作机械生成全部组合，但必须记录为什么纳入或排除。

### 5.6 用例数据不写死真实业务值

账号、组织、供应商、金额范围、业务日期等应引用测试数据 profile、枚举或生成策略；秘密不得进入用例。

## 6. AI 用例流水线

推荐建立以下流水线：

```text
需求/规则/现有用例
  → 业务事实抽取
  → 测试点设计
  → 用例草稿
  → 静态校验和缺口提问
  → UI/API/DB 探测与绑定
  → 可执行性评分
  → 人工业务审批
  → 编译执行
  → 结果反馈和用例修正
```

### 6.1 输入摄取

支持 PRD、需求单、Excel、接口文档、源码、数据库 schema、页面录制和历史缺陷。每条抽取事实都保留来源，不允许 AI 把推测写成已确认规则。

### 6.2 测试点设计

从以下维度构造测试点：

- 业务状态机；
- 输入等价类和边界值；
- 角色/组织/租户权限；
- 上下游对象关系；
- 幂等和重复操作；
- 异步和最终一致性；
- 审计、副作用和清理；
- 历史缺陷和变更风险。

### 6.3 用例草稿

AI 只生成 `draft`。无法确定的内容写入 `open_questions`，不能自行填充：

```yaml
open_questions:
  - id: Q-001
    question: 已审批需求是否允许跨部门发布策略？
    blocks: [strategy-publish-cross-department]
    source_gap: PRD 未说明
```

### 6.4 缺口提问

问题必须去重、一次性分组，并优先查询 approved knowledge。只询问会改变断言、前置条件、权限或清理方式的问题。

### 6.5 执行绑定

通过页面录制、网络抓包、OpenAPI、源码和数据库 schema，将业务断言绑定到 proof。绑定失败时用例保持 draft/blocked，不能因为 AI 给出了一段合理描述就标 READY。

### 6.6 反馈闭环

执行结果分为：业务 FAIL、环境错误、前置失败、能力漂移、规格错误和清理失败。只有确认是规格问题时才修改用例；真实业务缺陷不能通过修改预期来“修复”。

## 7. 用例质量评分

建议将现有评分升级为六个维度，每项满分如下：

| 维度 | 分值 | 核心问题 |
|---|---:|---|
| 业务明确性 | 20 | 目标、规则、角色和 under_test 是否明确 |
| 前置可准备性 | 20 | 对象、状态、条件、策略和输出是否完整 |
| 断言可判定性 | 20 | 是否为结构化 oracle，是否避免含糊预期 |
| 执行可绑定性 | 15 | UI/API/DB proof 是否可定位 |
| 安全与生命周期 | 15 | 副作用、幂等、清理/补偿是否明确 |
| 追踪与维护性 | 10 | 来源、版本、标签、变更影响是否可追踪 |

评分状态建议：

```text
0–49   INCOMPLETE：不能执行
50–69  DESIGN_READY：测试设计可评审，尚不能执行
70–84  BINDING_READY：可做页面/API/DB 绑定
85–94  EXECUTION_CANDIDATE：完成绑定，等待人工审批
95–100 READY：已审批，可正式执行
```

注意：高分不是自动审批。任何业务真相、写入边界或清理方式未确认，都不能进入 READY。

## 8. 我的明确诉求

为了让我稳定做好用例设计和执行，项目需要提供以下输入。按优先级划分：

### P0：没有就不能稳定做

1. **业务状态和转换规则**：每个对象有哪些状态，谁可以从哪个状态推进到哪个状态。
2. **角色和数据权限矩阵**：角色、组织、租户、数据范围和审批权限。
3. **最小可验收结果**：每个节点成功和失败分别必须出现什么状态、编号、关联和提示。
4. **前置对象约束**：下游需要什么上游对象、状态、字段和有效期。
5. **测试环境边界**：环境指纹、测试账号、数据库只读/写权限和外部系统沙箱。
6. **清理/补偿规则**：哪些可删除、取消、失效、冲正或只能人工处理。

### P1：显著提高效率和成功率

1. OpenAPI、接口文档或真实网络抓包；
2. 数据库 schema、主外键和状态字段说明；
3. 可录制的标准页面操作；
4. 字段字典、枚举和校验规则；
5. 历史缺陷和高风险业务规则；
6. 功能开关、租户配置和流程配置基线；
7. 一套经过业务确认的黄金样例数据。

### P2：提高覆盖和维护能力

1. 需求/规则稳定 ID；
2. 版本变更记录；
3. 线上脱敏样本和真实分布；
4. 运行失败、缺陷和 flaky 数据；
5. 能力 owner 和业务规则 owner。

## 9. 人与 AI 的职责边界

### 业务/产品负责

- 确认业务目标、规则、状态、角色和例外；
- 确认成功/失败判定；
- 确认不可逆副作用和清理政策；
- 审批业务层用例。

### 测试负责

- 风险分析、测试点取舍和优先级；
- 审查负向、边界、权限和幂等覆盖；
- 审核执行绑定和证据是否能证明业务结论；
- 处理未知结果和真实缺陷。

### AI 负责

- 读取需求、代码、接口、数据库和历史用例；
- 抽取事实并标记来源；
- 生成测试点和 canonical 草稿；
- 发现歧义、冲突和覆盖缺口；
- 推荐武器能力、断言和证据绑定；
- 根据执行反馈定位规格问题。

### 确定性工具负责

- schema 校验、哈希、审批、计划编译；
- UI/API/DB 执行；
- 断言、证据、清理和报告；
- 阻止未确认内容进入 READY。

## 10. 落地路线

### Phase 0：定义 v2 用例契约

- 扩展 canonical DSL：`traceability`、`intent`、`preconditions`、`action`、`oracles`、`wait`。
- 保持 v1 兼容，提供迁移器，不直接破坏现有用例。
- 定义结构化 oracle 和前置对象 schema。
- 建立含糊词检查器和 open question 机制。

### Phase 1：用例审计器

- 输入现有 Excel/canonical 用例；
- 输出质量评分、歧义、缺失事实、重复用例和覆盖矩阵；
- 生成一次性业务问题清单；
- 先不执行真实系统。

### Phase 2：AI 草拟与知识闭环

- 从需求/规则生成测试点和 draft 用例；
- 每个事实保留来源；
- 问题回答进入 knowledge，审批后回填；
- 禁止无来源推断进入 ready。

### Phase 3：探测和执行绑定

- 结合录制、抓包、OpenAPI、源码、DB schema 绑定 proof；
- 自动生成 assertion binding 候选；
- readiness 明确展示“业务缺口”和“技术绑定缺口”。

### Phase 4：武器库依赖接入

- `preconditions` 编译为武器库查询/创建计划；
- 用例下游变量绑定上游对象输出；
- 区分前置失败和目标 FAIL；
- 增加数据血缘和补偿检查。

### Phase 5：执行反馈优化

- 统计不可执行原因、能力漂移、规格错误、环境错误和 flaky；
- 识别高频问题并修订模板、知识或能力；
- 用真实执行数据衡量用例质量，而不是只看文档完整度。

## 11. 开发检查点

| 检查点 | 验收内容 |
|---|---|
| UC-00 | 现有用例基线审计完成，READY 比例和缺口分类可复现 |
| UC-01 | v2 schema、示例和 v1→v2 迁移器通过测试 |
| UC-02 | 含糊预期、缺少角色、缺少前置对象等问题能被静态发现 |
| UC-03 | AI 生成的事实全部有来源或 open question |
| UC-04 | 业务断言能绑定 UI/API/DB proof，绑定不足不能 READY |
| UC-05 | 前置对象能编译为武器库计划并传递输出 |
| UC-06 | 执行报告正确区分规格、前置、环境、目标和清理失败 |
| UC-07 | 用真实项目做三轮反馈后，评分与实际成功率正相关 |

每个检查点输出：

```text
reports/case-quality/UC-xx.json
问题数量和分类
输入/输出样例
自动测试结果
人工评审结果
遗留问题和 owner
```

## 12. 衡量指标

上线前记录当前基线，上线后按月比较：

| 指标 | 建议目标 |
|---|---:|
| 首次导入后可达到 DESIGN_READY 的比例 | ≥80% |
| 经一次业务澄清后达到 BINDING_READY 的比例 | ≥70% |
| 已审批 READY 用例首次执行成功率 | ≥85% |
| 因用例歧义导致的 INVALID_SPEC | 下降 60% |
| 人工补齐单条用例平均耗时 | 下降 50% |
| 前置失败误报为目标 FAIL | 0 |
| 无来源业务规则进入 READY | 0 |
| 需求/规则到用例可追踪率 | ≥95% |
| 重复或等价用例比例 | 下降 30% |
| 执行后可自动归因比例 | ≥90% |

## 13. 风险和约束

1. AI 可以提高结构化效率，但不能创造业务真相。
2. 输入资料互相冲突时，必须阻塞并交由 owner 处理。
3. 用例过细会导致数量爆炸，需要风险优先级和组合削减。
4. 用例过粗会导致失败无法定位，应坚持单一 under_test。
5. 页面录制只能生成执行草稿，不能替代业务断言。
6. 数据库字段不能直接等同于业务概念，需要映射和审批。
7. 高分用例仍可能依赖不健康能力，质量评分和运行健康度必须分开。
8. 需求持续变化时，应通过 traceability 做影响分析，而不是人工逐条查找。

## 15. 最终建议

用例是目前影响执行效率和成功率的关键瓶颈，但不是最终无法突破的瓶颈。真正的上限取决于三件事：

1. 业务真相是否能以稳定 ID、状态和规则提供；
2. 前置数据是否能由武器库可靠准备；
3. 业务断言是否能绑定独立、可重复的 UI/API/DB 证据。

建议与武器库并行推进，但先后顺序是：

```text
先做用例 v2 契约和审计器
  → 再做 requirement.create 武器
  → 再把用例 preconditions 编译到武器库
  → 最后扩展 1+2、1+2+3 累计链路
```

如果只做武器库，不改善用例，系统会“有很多武器但不知道该选哪个、为什么选、成功如何判定”；如果只改善用例，不做武器库，用例会“描述得很清楚但前置数据无法稳定准备”。两者必须以结构化前置对象和输出变量为接口同步建设。
